# 1. Executive Summary

The Manufacturing Data Lakehouse is an end-to-end Data Engineering project designed to consolidate data from multiple manufacturing operational systems into a centralised analytical platform.

A manufacturing enterprise operates multiple factories and uses independent systems to manage production, inventory, machinery, quality inspections and maintenance.

These systems generate substantial volumes of structured and semi-structured data. However, the information is distributed across different databases and file formats, making consolidated reporting and business analysis difficult.

The proposed solution introduces a centralised Data Lakehouse that:

- Collects data from multiple independent sources.
- Stores raw data in a centralised storage layer.
- Processes and cleans data using PySpark.
- Organises data into Bronze, Silver and Gold layers.
- Supports incremental data ingestion.
- Provides reliable, analytics-ready datasets.
- Enables manufacturing performance analysis.
- Supports future batch and streaming workloads.

The project will initially run on a local Windows development environment and will be designed to support future cloud deployment.

# 2. Business Scenario

Consider a heavy equipment manufacturing company operating five manufacturing facilities.

The company manufactures industrial machinery and equipment using different production lines.

Each facility maintains operational information through independent systems.

For example:

| Operational system | Information maintained |
|---|---|
| Production Management | Production orders and manufacturing output |
| Inventory Management | Raw materials, components and stock levels |
| Machine Monitoring | Machine temperature, vibration and operational status |
| Quality Management | Product inspections and defects |
| Maintenance Management | Machine breakdowns, repairs and maintenance costs |

Currently, management cannot easily obtain a consolidated view of manufacturing operations.

The company wants a centralised platform that integrates these datasets and provides consistent, reliable information for business analysis.

Our Manufacturing Data Lakehouse will solve this problem.

# 6. High-Level Architecture

The system will follow a Medallion Lakehouse architecture.

## 6.1 Master Architecture

Data Sources → Python Extraction → Landing (immutable batches) → Spark → Bronze Layer → Silver Layer → Gold Layer → Data Consumption

```text
 SOURCES                      EXTRACTION (Python)          LANDING              LAKEHOUSE (PySpark + Delta Lake)
+---------------------------+
| PostgreSQL                |
|  production schema        |  watermark: updated_at > last - overlap
|  inventory schema         |----+
|  maintenance schema       |    |   +-------------------+   +-------------+   +--------+   +--------+   +------+
+---------------------------+    +-->| batched extract   |-->| data/       |-->| BRONZE |-->| SILVER |-->| GOLD |
| CSV  (quality: nightly    |----+   | + batch metadata  |   | landing/    |   | raw +  |   | clean, |   | facts|
|       inspection export)  |    |   | + watermark state |   | one folder  |   | ingest |   | dedup, |   | dims,|
+---------------------------+    |   +-------------------+   | per batch,  |   | meta,  |   | conform|   | KPIs |
| JSON (sensors: nested,    |----+                           | never       |   | dirt   |   | soft-  |   |      |
|       high-volume events) |                                | rewritten   |   | kept   |   | delete |   |      |
+---------------------------+                                +------+------+   +--------+   +--------+   +------+
                                                                    |              ^
                                                                    +-- replay ----+  (re-run Bronze without
                                                                                        querying the source)
```

### Layer 1: Data Sources

Independent operational systems:

- Production Management System.
- Inventory Management System.
- Machine Monitoring System.
- Quality Management System.
- Maintenance Management System.

### Layer 2: Data Ingestion

Python will extract data from:

- PostgreSQL databases.
- CSV files.
- JSON files.
- Future APIs and streaming sources.

Responsibilities:

- Extract source records, reading PostgreSQL in batches rather than loading whole tables into memory.
- Validate source structure.
- Capture ingestion timestamps.
- Identify new or modified records using a watermark with an overlap window (AD-2).
- Write each extraction as an immutable batch in `data/landing/` (AD-4).
- Record ingestion status, watermark state and failures.

Spark, not Python, reads landed batches and writes Bronze Delta tables. This gives the pipeline a recovery point: if Spark fails, the batch can be replayed from landing without querying the source again.

### Layer 3: Bronze Layer

The Bronze layer stores raw ingested data.

Characteristics:

- Preserves source information.
- Maintains ingestion metadata.
- Supports historical data retention.
- Allows reprocessing.
- Stores data in Delta Lake format.

No unnecessary business transformations should be performed at this stage. Dirty data, such as duplicates, bad identifiers and invalid values, is preserved in Bronze and resolved in Silver (AD-3). Bronze ingestion must be idempotent: re-ingesting the same landing batch must not create duplicates.

### Layer 4: Silver Layer

The Silver layer contains cleaned and standardised data.

Responsibilities:

- Handle missing values.
- Remove duplicate records.
- Validate data types.
- Standardise timestamps.
- Validate business rules.
- Resolve inconsistent identifiers.
- Apply necessary transformations.
- Handle schema evolution.

### Layer 5: Gold Layer

The Gold layer contains business-ready datasets.

Examples:

- Daily Production Summary.
- Factory Performance.
- Inventory Availability.
- Machine Utilisation.
- Machine Downtime.
- Product Defect Rates.
- Maintenance Cost Analysis.

The Gold layer will use appropriate fact and dimension modelling.

### Layer 6: Data Consumption

Gold datasets will be available for:

- SQL queries.
- Business intelligence dashboards.
- Manufacturing reports.
- Analytical applications.
- Future AI-powered applications.

# 7. Source Systems and Data Requirements

Five source systems will be simulated (AD-1).

| Source system | Technology | Data | Owns master data | Change detection |
|---|---|---|---|---|
| Production | PostgreSQL schema `production` | Production orders, production records | Factory, Product | `updated_at` watermark |
| Inventory | PostgreSQL schema `inventory` | Warehouses, inventory transactions | Warehouse | `updated_at` watermark |
| Quality | CSV files | Inspection records (simulated nightly export) | none | New export files |
| Maintenance | PostgreSQL schema `maintenance` | Maintenance records | Machine | `updated_at` watermark |
| Machine Monitoring | JSON files | High-volume nested sensor readings | none | New files; `event_id` deduplication |

The three PostgreSQL systems run in one local PostgreSQL instance, but each gets its own schema so they behave like independent operational systems. Each master entity has exactly one owning system. Other systems refer to it by ID only and keep no copy. For example, the Inventory system refers to `product_id` but does not own a product table.

# 8. Initial Data Model

The following entities will form the initial source database.

| Entity | Primary Key | Important Relationships |
|---|---|---|
| Factory | factory_id | Referenced by machines and orders |
| Machine | machine_id | References factory |
| Product | product_id | Referenced by orders and inspections |
| Production Order | order_id | References factory and product |
| Production Record | record_id | References production order |
| Warehouse | warehouse_id | References factory |
| Inventory Transaction | transaction_id | References product and warehouse |
| Sensor Reading | reading_id | References machine |
| Quality Inspection | inspection_id | References product and order |
| Maintenance Record | maintenance_id | References machine |

Ownership and storage, following AD-1:

| Entity | Owning system | Stored as |
|---|---|---|
| Factory, Product, Production Order, Production Record | Production | PostgreSQL `production` |
| Warehouse, Inventory Transaction | Inventory | PostgreSQL `inventory` |
| Machine, Maintenance Record | Maintenance | PostgreSQL `maintenance` |
| Quality Inspection | Quality | CSV |
| Sensor Reading | Machine Monitoring | JSON |

Every mutable PostgreSQL table has `created_at`, `updated_at` and `is_deleted` columns (AD-2). Rows are soft-deleted, never hard-deleted. Each sensor event carries an `event_id` and an `event_timestamp`. The pipeline adds an `ingestion_timestamp` when it ingests the event.

Detailed column definitions, constraints and relationship diagrams will be maintained in the database design specification.

# 9. Data Generation Strategy

Public datasets and synthetic datasets will be used.

The initial implementation will generate realistic manufacturing data programmatically using Python.

Initial target volumes:

| Dataset | Target records |
|---|---:|
| Factories | 5 |
| Machines | 100 |
| Products | 500 |
| Production Orders | 100,000 |
| Inventory Transactions | 200,000 |
| Sensor Readings | 1,000,000 |
| Quality Inspections | 100,000 |
| Maintenance Records | 20,000 |

The generation process must preserve referential integrity.

For example:

- Every machine must belong to an existing factory.
- Every production order must reference a valid product and factory.
- Every sensor reading must reference an existing machine.
- Every maintenance record must reference an existing machine.

Data generation must support batch writing to avoid excessive memory consumption.

The generator must be deterministic (`--seed`) and must simulate change over time, not just one static load (AD-2):

| Run | Scenario |
|---|---|
| 1 | Initial full load |
| 2 | New records inserted |
| 3 | Existing records updated |
| 4 | Late-arriving records |
| 5 | Soft-deleted records |
| 6 | Re-running the same batch, which must be idempotent |

It must also support configurable corruption, plus a clean mode that turns corruption off (AD-3):

```text
python scripts/generate_data.py --dirty-rate 0.02 --seed 42
```

| Data issue | Example |
|---|---|
| Duplicate records | Same `inspection_id` twice |
| Inconsistent IDs | `FAC-001` vs `fac_1` |
| Missing values | Null `product_id` |
| Invalid quantities | -50 units |
| Invalid sensors | Temperature beyond permitted range |
| Mixed time zones | UTC and local timestamps |
| Schema drift | New optional JSON fields |

Future datasets may scale to five or ten million sensor readings for performance experiments.

# 11. Data Pipeline Requirements

## 11.1 Initial Batch Processing

The initial system will support scheduled batch ingestion.

Example:

1. Source data becomes available.
2. Python extracts the records in batches.
3. Ingestion metadata is generated.
4. Each extraction is written to `data/landing/` as an immutable batch.
5. Spark reads the landed batch and writes Bronze Delta tables.
6. Transformations produce Silver datasets.
7. Business aggregations produce Gold datasets.
8. Data quality checks are executed.
9. Pipeline execution status is recorded.

A Python runner executes these steps (AD-5). It starts as a simple sequential runner and later becomes dependency-aware. Airflow DAGs come only after the pipeline's dependencies are understood (Milestone 8).

## 11.2 Incremental Data Processing

The pipeline must eventually support incremental loading.

Instead of reprocessing all historical data, it should identify and process only newly inserted or modified records.

Possible mechanisms:

- Timestamp-based extraction.
- Incrementing primary-key watermarks.
- Change Data Capture.

The initial implementation will use timestamp-based incremental extraction (AD-2), hardened as follows:

- **Overlap window.** Extract rows where `updated_at > last_watermark - overlap`, so rows committed late around the boundary are not missed.
- **Stable primary keys and deterministic deduplication.** Because of the overlap, a row can be extracted twice. A rule based on the key plus the latest `updated_at` collapses the copies.
- **Soft deletes.** `is_deleted = true` is an ordinary update, so the watermark picks it up and the delete propagates to Silver.
- **Known limitation.** A hard delete cannot be detected without CDC or a separate deletion feed. Source systems must therefore never hard-delete.
- **Sensor JSON.** `event_id` identifies duplicate events. Comparing `event_timestamp` with `ingestion_timestamp` identifies late arrivals.
- **Quality CSV.** Each nightly export file is one unit of change. The pipeline tracks which files have been processed.

## 11.3 Failure Handling

The system should handle:

- Database connection failures.
- Invalid source records.
- Duplicate data.
- Missing columns.
- Incorrect data types.
- Failed transformations.
- Partial pipeline execution.
- Repeated ingestion attempts.

Pipeline failures must be logged with enough information for investigation and recovery.

# 22. Architecture Decision Log

| ID | Area | Decision | Rationale |
|---|---|---|---|
| AD-1 | Source systems | Production, Inventory and Maintenance in PostgreSQL, each in its own schema. Quality as CSV. Sensors as JSON. Each master entity has one owning system. | JSON suits nested, high-volume sensor data. CSV brings type-guessing and schema drift. Separate schemas imitate independent systems while running on one database. |
| AD-2 | Incremental loading | `created_at`, `updated_at` and `is_deleted` on every mutable table. Watermark with an overlap window. Stable keys and deterministic deduplication. Event IDs for sensor data. | A timestamp watermark alone misses boundary rows and hard deletes. Incremental loading has to be designed into the source data. |
| AD-3 | Dirty data | The generator takes `--dirty-rate` and `--seed` and also has a clean mode. Dirt is preserved in Bronze and resolved in Silver. | Silver and the data quality checks need real failures to catch. |
| AD-4 | Bronze writer | Python extracts to landing, then Spark writes Bronze. Direct JDBC ingestion can be studied later. | Batches can be replayed without the source, gives a recovery point, and handles PostgreSQL, CSV and JSON the same way. |
| AD-5 | Orchestration | A Python runner first, then dependency-aware execution, then Airflow. | Understand pipeline dependencies before adopting a scheduler. Airflow needs Docker or WSL on Windows. |
| AD-6 | Windows risk | The environment spike runs before any other development. Fall back to WSL2 or Docker rather than debug Windows. | PySpark, Delta, Java and winutils compatibility is the biggest technical risk. |
| AD-7 | Naming | Repository `forge-lake`, Python package `forgelake`. | Matches the project name. |

**Guiding principle:** every feature must solve a real Data Engineering problem and demonstrate a concept that matters in production. Partition tables only when query patterns and data volume justify it. Introduce Kafka only for a real streaming requirement. Introduce Airflow only once pipeline dependencies are understood. Use large volumes only to answer a performance question, not to claim Big Data experience.
